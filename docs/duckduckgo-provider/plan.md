## Order of work
1. Add a DuckDuckGo client dependency with TypeScript declarations and install a reproducible lockfile.
2. Refactor existing credential discovery so auto mode can test availability without throwing, while explicit legacy-provider mode keeps its actionable error.
3. Add provider selection and the DuckDuckGo adapter, mapping its result shape into the existing shared model and combining caller cancellation with timeout.
4. Keep shared output provider-neutral and include provider identity only in structured details.
5. Add deterministic tests with no live web dependency.
6. Update README configuration examples.
7. Run tests, TypeScript checking, and a package dry-run; review the diff for credentials and accidental public provider leakage.

## Risks
- Most dangerous: auto routing could change behavior for current users. Mitigation: existing credentials have precedence, so current configured users remain on the existing backend.
- DuckDuckGo may rate-limit scraping or change response markup. Mitigation: rely on a focused client library, cap timeout, and expose failures clearly.
- Cancellation may not propagate through the third-party client. The adapter will bridge the pi abort signal into the client's request cancellation where supported; tests will cover already-aborted and in-flight abort behavior if the client API permits.
- Alternative rejected: port deer-flow's Python `ddgs` package or spawn Python. That adds a second runtime and installation dependency to a TypeScript pi extension.
- Alternative rejected: replace the current provider outright. This would regress Chinese coverage and configured deployments.
